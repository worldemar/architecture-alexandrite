# Задание 2. Выбор и настройка мониторинга в системе

## Контекст и цели

Система "Александрит" состоит из трёх приложений:
- онлайн-магазин (Vue + Java Spring Boot)
- CRM (Vue + Java Spring Boot)
- MES (React + C#)
а также инфраструктурных компонентов (RabbitMQ, отдельные БД для каждого приложения, S3-хранилище 3D-моделей, Managed DB в Yandex Cloud).

Нагрузка растёт линейно, открытие внешнего API привело к всплеску запросов и росту числа просроченных/"потерянных" заказов. Сейчас наблюдаемость почти отсутствует: есть только Яндекс Метрика для B2C-части, которая не покрывает B2B-API и внутренние процессы.

Цель этого документа - описать, **какой мониторинг внедрить**, **какие метрики собирать** и **какими шагами реализовать решение**, чтобы:
- вовремя обнаруживать технические и бизнес-проблемы
- понимать реальную нагрузку и запас по производительности
- измерять эффект от архитектурных изменений

В предлагаемом решении **Яндекс Метрику не подразумевается отключать**, а описываемый дальше серверный мониторинг и бизнес-дашборды **дополняют её**, покрывая B2B-сценарии, внутренние процессы и техническое состояние сервисов.

---

## 1. Мотивация

Мониторинг нужен для решения следующих задач.

1. **Раннее обнаружение инцидентов и снижение MTTR.**
   - Сейчас команда узнаёт о проблемах от клиентов и партнёров
   - При наличии метрик и алертов мы сможем замечать деградации (ошибки, рост латентности, переполнение очередей) до массовых жалоб

2. **Понимание узких мест и планирование развития.**
   - Нужно объективно понимать, где "узкое горлышко": MES, расчёт стоимости, RabbitMQ, БД, внешнее API, сеть и т.д
   - Без метрик сложно обосновать необходимость масштабирования или оптимизаций (CPU, память, соединения к БД, размер БД, загрузка очередей)

3. **Поддержка SLA и доверия бизнеса.**
   - Бизнесу важно видеть показатели: время расчёта стоимости, время до старта производства, долю просроченных заказов, стабильность API для партнёров
   - Мониторинг позволит строить дашборды SLA и обсуждать проблемы на основе данных, а не ощущений

4. **Поддержка архитектурных инициатив.**
   - В Task1 выбрана инициатива по наблюдаемости (мониторинг, логирование, трейсинг) как одна из ключевых
   - Мониторинг - фундамент для дальнейших шагов: оптимизации MES, переработки расчёта стоимости, масштабирования и т.п

5. **Снижение нагрузки на поддержку и разработчиков.**
   - С понятными дашбордами и алертами часть инцидентов сможет диагностировать поддержка/DevOps без вовлечения всех разработчиков

## 2. Выбор подхода к мониторингу

В системе несколько типов компонентов, для них целесообразно сочетать разные подходы:
- **RED (Rate, Errors, Duration)** - для внешних и внутренних API
- **USE (Utilization, Saturation, Errors)** - для инфраструктурных ресурсов (CPU, память, сеть, БД)
- **"Четыре золотых сигнала" (latency, traffic, errors, saturation)** - как обобщающий подход для пользовательских сценариев и ключевых потоков (создание заказа, расчёт стоимости, изменение статуса)

### 2.1. Выбор подхода по компонентам

- **Интернет-магазин API (B2C)**
  - Основной подход: **RED** + "четыре золотых сигнала"
  - Важно: RPS, ошибки, латентность, насыщенность по ресурсам (CPU, память, соединения к БД), трафик

- **CRM API**
  - Основной подход: **RED** + "четыре золотых сигнала"
  - CRM менее нагружена, но критична для жизненного цикла заказа (подтверждение, закрытие)

- **MES API**
  - Основной подход: **RED** + "четыре золотых сигнала"
  - MES - узкое место по жалобам: важны задержки на дашборде, ошибки, насыщенность по ресурсам, RPS по ключевым эндпоинтам (список заказов, изменение статуса)

- **Внешний API для партнёров**
  - Основной подход: **RED**
  - Ключевые параметры: RPS по партнёру, доля ошибок, латентность, распределение запросов по партнёрам, endpoint-ам

- **RabbitMQ**
  - Основной подход: **USE**
  - Важно: количество сообщений "в полёте", в очередях, в dead-letter, ошибки при доставке

- **Базы данных (shop db, MES db)**
  - Основной подход: **USE**
  - Важно: утилизация CPU/памяти, количество подключений, размер БД, блокировки

- **Инфраструктура (EC2-инстансы, сеть, S3)**
  - Основной подход: **USE**
  - Важно: CPU, память, дисковая подсистема, сетевой трафик, размер S3-хранилища

- **Бизнес-процессы и заказы**
  - Основной подход: "четыре золотых сигнала" + бизнес-метрики
  - Важно: скорость прохождения по статусам, количество просроченных заказов, "зависшие" статусы

## 3. Метрики и части системы (с ярлыками)

Ниже выбраны метрики (частично из предложенного списка), сгруппированные по подсистемам. Для каждой указано:
- **зачем** она нужна
- **ярлыки (labels)**, которые планируется использовать

### 3.1. RabbitMQ

- **Number of `dead-letter-exchange` letters in RabbitMQ**
  - Зачем: индикатор проблем с доставкой сообщений (например, некорректные сообщения, ошибки обработки, неверная маршрутизация). Рост - сигнал о логических ошибках в интеграции и отказах сервисов-потребителей
  - Ярлыки:
    - `exchange` (имя exchange)
    - `queue` (имя очереди)
    - `reason` (причина DLQ, если доступно)
    - `env` (dev/release/prod)
    - `service_consumer` (MES/CRM и т.п.)

- **Number of message `in flight` in RabbitMQ**
  - Зачем: показывает текущую нагрузку на систему обработки сообщений и риск переполнения очередей. Помогает видеть "пробку" при всплесках заказов
  - Ярлыки:
    - `queue`
    - `routing_key`
    - `env`
    - `service_producer`, `service_consumer`

### 3.2. API интернет-магазина, CRM и MES

#### 3.2.1. Нагрузка и производительность

- **Number of requests (RPS) for internet shop API / CRM API / MES API**
  - Зачем: базовый показатель нагрузки на каждый API, помогает видеть пики, планировать масштабирование и rate limiting
  - Ярлыки:
    - `service` (shop, crm, mes)
    - `endpoint` (укрупнённо, например `/orders/*`, `/orders/{id}/status`)
    - `method` (GET/POST/PUT/DELETE)
    - `env`
    - `client_type` (web, internal, partner, operator)

- **Number of requests (RPS) per user for internet shop API / CRM API / MES API**
  - Зачем: позволяет выявлять "шумных" клиентов (например, партнёра, который перегружает API) и потенциальные аномалии/атаки
  - Ярлыки:
    - `service`
    - `user_id` / `partner_id` (в анонимизированном виде)
    - `env`

- **Response time (latency) for shop API / CRM API / MES API**
  - Зачем: ключевой показатель пользовательского опыта. Особенно важно для:
    - страницы заказов операторов MES
    - операций создания заказа
    - операций расчёта стоимости (если они пока синхронны)
  - Ярлыки:
    - `service`
    - `endpoint`
    - `method`
    - `status_code_group` (2xx/4xx/5xx)
    - `env`
    - `client_type`

- **Number of `HTTP 200` / `HTTP 500` for shop API / CRM API / MES API**
  - Зачем: для расчёта доли успешных и неуспешных запросов, определения SLO по ошибкам
  - Ярлыки:
    - `service`
    - `endpoint`
    - `method`
    - `env`
    - `client_type`

- **Number of simultaneous sessions for shop API / CRM API / MES API**
  - Зачем: даёт представление о количестве активных пользователей/сессий, помогает планировать ёмкость и оценивать эффект от маркетинговых кампаний/новых партнёров
  - Ярлыки:
    - `service`
    - `env`
    - `user_type` (b2c, operator, admin, partner)

#### 3.2.2. Ресурсы приложений

- **CPU % for shop API / CRM API / MES API**
  - Зачем: позволяет вовремя увидеть насыщение по процессору и оценить необходимость вертикального/горизонтального масштабирования
  - Ярлыки:
    - `service`
    - `instance_id`
    - `env`
    - `node` (если есть)

- **Memory Utilisation for shop API / CRM API / MES API**
  - Зачем: выявление утечек памяти, выбор корректных лимитов в контейнерах/VM, оценка запаса по ресурсам
  - Ярлыки:
    - `service`
    - `instance_id`
    - `env`

- **Kb tranferred (received) / Kb provided (sent) for shop/CRM/MES API**
  - Зачем: понимание сетевой нагрузки, особенно для тяжёлых операций (загрузка/выгрузка 3D-моделей, больших отчётов)
  - Ярлыки:
    - `service`
    - `direction` (in/out)
    - `env`

### 3.3. Базы данных

- **Memory Utilisation for shop db instance / MES db instance (и аналогично для CRM)**
  - Зачем: оценка потребления ресурсов БД, выявление ситуаций, когда БД становится узким местом
  - Ярлыки:
    - `db` (shop, mes, crm)
    - `env`
    - `instance_id`

- **Number of connections for shop db instance / MES db instance**
  - Зачем: контроль количества подключений от приложений, предотвращение исчерпания лимитов и деградации
  - Ярлыки:
    - `db`
    - `env`
    - `service` (кто подключается)

- **Size of shop db instance / MES db instance**
  - Зачем: контроль роста объёма данных, планирование архивации и масштабирования хранилища
  - Ярлыки:
    - `db`
    - `env`

### 3.4. Хранилище файлов

- **Size of S3 storage**
  - Зачем: контроль роста хранилища 3D-моделей, планирование бюджета и политики хранения (архивация, очистка)
  - Ярлыки:
    - `bucket`
    - `env`

### 3.5. Бизнес-метрики заказов (дополнительно к списку)

Эти метрики не перечислены явно в заданном списке, но критичны для бизнеса:

- **Количество заказов по статусам (`INITIATED`, `SUBMITTED`, `PRICE_CALCULATED`, ..., `CLOSED`)**
  - Зачем: даёт профиль "воронки" заказов, позволяет увидеть, где заказы "застревают"
  - Ярлыки:
    - `status`
    - `env`
    - `channel` (b2c, b2b_api)
    - `partner_id` (для b2b)

- **Среднее и p95 время пребывания заказа в каждом статусе**
  - Зачем: измерение SLA по жизненному циклу заказа, поиск этапов с максимальной задержкой (например, между `SUBMITTED` и `PRICE_CALCULATED`, между `MANUFACTURING_APPROVED` и `MANUFACTURING_STARTED`)
  - Ярлыки:
    - `status_from`, `status_to`
    - `env`
    - `channel`
    - `partner_id`

- **Количество просроченных заказов (по отношению к обещанным 3 неделям, например, таргетное значение можно отрегулировать)**
  - Зачем: прямая бизнес-метрика удовлетворённости клиентов и качества работы процессов
  - Ярлыки:
    - `env`
    - `channel`
    - `partner_id`

- **Количество "зависших" заказов (без изменения статуса > X часов/дней)**
  - Зачем: помогает находить "потерянные" заказы и настраивать оповещения/эскалацию
  - Ярлыки:
    - `status`
    - `env`
    - `channel`

## 4. План действий

### 4.1. Выбор и развёртывание стека мониторинга

- Определить технологический стек:
  - метрики: **Prometheus + Alertmanager** (или управляемый аналог в Yandex Cloud)
  - визуализация: **Grafana** (или аналогичная система дашбордов)
- Настроить базовую инфраструктуру:
  - развёртывание Prometheus/Grafana (желательно как инфраструктурный сервис, а не внутри одного из приложений)
  - настройка резервного копирования и обновлений

### 4.2. Инструментирование приложений

- Для интернет-магазина, CRM и MES:
  - включить/добавить метрики HTTP-запросов (RPS, latency, коды ответов) через стандартные библиотеки (Micrometer для Spring Boot, Prometheus-metrics для .NET и т.п.)
  - добавить бизнес-метрики заказов (статусы, времена переходов) в виде custom-метрик
- Для внешнего API:
  - добавить ярлыки `partner_id`, `plan` (тариф/уровень партнёра) для анализа RPS и ошибок по партнёрам

### 4.3. Сбор метрик RabbitMQ и БД

- Подключить стандартные экспортёры:
  - RabbitMQ exporter для Prometheus
  - DB exporter (PostgreSQL/MySQL в зависимости от используемых БД)
- Настроить сбор метрик `dead-letter`, `messages in flight`, подключений и размера БД

### 4.4. Дашборды

Создать первичные дашборды:
- **Дашборд по API**:
  - RPS, ошибки, латентность по shop/CRM/MES, разрезы по endpoint-ам и клиентам/партнёрам
- **Дашборд по MES-дашборду операторов**:
  - латентность ключевых запросов (список заказов), нагрузка на MES, запросы к БД, RPS по дашборду
- **Дашборд по очередям и БД**:
  - RabbitMQ (dead-letter, in-flight), ресурсы и соединения БД
- **Бизнес-дашборд по заказам**:
  - количество заказов по статусам, времена переходов, просрочки, зависшие заказы

### 4.5. Алерты

- Настроить Alertmanager/аналоги:
  - алерты по техническим метрикам (ошибки 5xx, рост латентности, переполнение очередей, насыщение по CPU/памяти)
  - алерты по бизнес-метрикам (рост доли просроченных заказов, рост количества зависших заказов)
- Интегрировать уведомления:
  - Slack/Telegram/почта, система тикетов (Jira и т.п.)

### 4.6. Внедрение в процесс

- Согласовать с бизнесом и командами:
  - какие SLO/SLA по основным метрикам считаются приемлемыми
  - какие алерты должны считаться инцидентами P1/P2 и т.д
- Зафиксировать несколько ключевых **SLO верхнего уровня**, например:
  - **латентность MES-дашборда операторов**: p95 не более 2 секунд в рабочие часы
  - **стабильность внешнего API для партнёров**: доля `HTTP 5xx` не более 0,5-1% за сутки
  - **качество выполнения заказов**: доля просроченных заказов (по отношению к целевому сроку, сейчас 3 недели) не более оговорённого порога (значение согласуется с бизнесом и может меняться по мере роста компании)
- Обучить команду пользоваться дашбордами и метриками

### 4.7. Процесс поддержки и эволюции мониторинга

- Назначить ответственных за мониторинг:
  - **владельца метрик и SLO** со стороны продукта/бизнеса
  - **технического владельца стека мониторинга** (DevOps/архитектор)
- Зафиксировать регулярный цикл пересмотра:
  - **еженедельный** короткий просмотр алертов и инцидентов (что "шумит", какие пороги нужно скорректировать)
  - **ежемесячный** или **ежеквартальный** обзор дашбордов и ключевых метрик вместе с бизнесом: актуальность SLO, достижимость целей, новые потребности
- Ввести простой рабочий процесс изменений:
  - любые новые продуктовые или архитектурные инициативы сопровождаются обновлением набора метрик и SLO
  - изменения в метриках, порогах и алертах оформляются через задачи в трекере (Jira и т.п.), проходят ревью и документируются
- Обеспечить прозрачность:
  - хранить описание метрик, SLO и текущих порогов в общем репозитории (confluence/репозиторий документации)
  - периодически (например, раз в квартал) актуализировать этот документ по результатам пересмотров

## 5. Показатели насыщенности и реакции системы

Ниже пример базового набора пороговых значений насыщенности (Saturation) и действий при их превышении. Значения могут быть уточнены после первых недель сбора метрик.

### 5.1. Примеры порогов

- **CPU % for MES API > 80% в течение 5 минут**
  - Риск: деградация отклика дашборда операторов и операций изменения статуса
  - Действия:
    - автоматически масштабировать количество инстансов MES (если есть автоскейлинг)
    - при отсутствии автоскейлинга - алерт в канал поддержки/DevOps с рекомендацией ручного масштабирования
    - заведение тикета на анализ нагрузки и оптимизацию

- **Number of message `in flight` in RabbitMQ для очередей расчёта стоимости > X (порог вычисляется эмпирически)**
  - Риск: накапливается очередь расчёта стоимости, заказы долго не переходят в `PRICE_CALCULATED`
  - Действия:
    - алерт DevOps/разработчикам
    - при возможности - временное увеличение количества воркеров (консьюмеров)
    - анализ входящего RPS по внешнему API (возможно, требуется ужесточить rate limiting)

- **Response time (latency) for MES API (дашборд заказов) p95 > 2 сек в течение 10 минут**
  - Риск: операторы не могут оперативно брать новые заказы в работу
  - Действия:
    - алерт команде разработки MES
    - включение временного ограничения глубины выборки (меньше записей на страницу) или упрощение фильтров (если возможно)
    - анализ запросов к БД (проверка планов, индексов)

- **Доля `HTTP 500` для внешнего API > 1% за 5 минут**
  - Риск: партнёры массово не могут оформить заказы/рассчитать стоимость, потеря контрактов
  - Действия:
    - алерт P1, уведомление ответственных за партнёрский API
    - при необходимости - временное ограничение нагрузки (rate limiting, отключение части неключевых функций)
    - сбор дополнительной информации (логи, трейсинг) для быстрой диагностики

- **Количество заказов, находящихся в одном статусе > N часов (например, `SUBMITTED` > 12 часов, `PRICE_CALCULATED` > 24 часов)**
  - Риск: заказы "зависли", клиенты не получают обновлений, растёт недовольство
  - Действия:
    - создание тикетов на разбор зависших заказов
    - уведомление ответственных менеджеров/операторов
    - анализ причин (инциденты с RabbitMQ, MES, CRM)

---

Документ описывает **только первую итерацию системы мониторинга**: после запуска и нескольких недель эксплуатации метрики и пороги будут уточняться, появятся дополнительные дашборды и алерты. Главное - создать сейчас **единый контур наблюдаемости**, который позволит команде и бизнесу видеть состояние системы и принимать обоснованные решения, отрегулировать таргетные и пороговые значения можно и позже, а с ростом бизнеса их даже необходимо будет менять (см. пункт 4.7).
